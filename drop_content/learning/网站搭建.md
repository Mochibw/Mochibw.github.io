本来在这个网站主体部分搭建完成之后，我就想要写一个关于网站搭建过程中出现的问题的总结，不过国庆的时候很大一部分时间在去玩和回家的路上，于是直到现在才开始写总结。

这个网站的所有搭建过程，包括选择框架、挑选配色、动态效果、页面布局、增加评论功能等，几乎全部是由 AI 完成，我在其中的角色是负责找到符合我喜好，且浏览效果好的方案，在 AI 出错的时候进行调整，使用 git 同步到 github 上。我在一天半的时间内完成了除评论区外的所有主体功能的开发，效率还是令我比较满意的。其中 git 提交的过程在我设想时是可以让 AI 完成，后来由于三个原因，我打算自己来进行提交。其一， Claude Code 在 git commit 时会夹带私货，将自己列入 contributor 里面；其二， AI 撰写的 commit 文本比较长，感觉有些冗余，不利于查找；其三，不知是不是我的错觉，在 claude 的命令行里执行命令有些缓慢，使用体验非常不好。

实际上，我使用 AI 编程完成一个完整项目的编写经验并不多，这是其中之一。平时主要是用它来实现某“个”功能，而非完整的项目。撰写这个总结，是想要在下次搭建项目时可以有一个能够借鉴的方案。

## AI 编程方案

现在我所使用的方案是：大部分时候使用 Claude Code + glm 4.6，在少数需要 claude sonnet 4.5 的时候使用 vscode + cline。就我个人的体验而言，glm 官方所说的 glm 4.6 与 claude sonnet 4 相当，其实所言非虚。在这次网站搭建过程中，出现了一些比较难修复的 bug，正好 claude 4.5 出来了，我便想用一用。大概花了 30 元，修好了 bug 之一，实在太贵了......使用 glm 主要是因为注册的时候送了很多免费 token，可以让我毫不心疼地一遍一遍尝试，修的不对就 git restore 重新开始，像游戏里 load 进度一样。在免费 token 用完后可能会考虑使用 glm 的编程套餐，20 元/月的套餐对于我一个不经常编程的人来说感觉非常便宜且额度够用。

## 提示词与上下文

提示词和上下文管理非常重要，以至于这句话看起来像是一句废话。实际体验中，好提示词的 glm 4.6 > 一般提示词的 claude 4.5。

> **每次只给 AI 一个任务，及时 git 保存进度。**

在编写个人网站的时候，出现了三个相互纠缠的 bug，开始时我想要给 AI 提供尽可能全面的信息，所以告诉它可以同时考虑到三个问题来进行修复，后来发现这种方式于事无补，它还是会在修复过程中牵一发而动全身，表面上可能解决了其中一个问题，实际三个问题仍然存在，即使是 claude 4.5 也不能很好地处理。后来使用 glm 4.6，一次只给 AI 单个问题，并准确详细地描述问题，可以依次把三个问题全部解决。尽管中间有时候修复不完全，但是可以通过人工引导，最终达到完全修复的效果。

> **提示词要像一个“标准”的人。**

这么说有点怪异。现在人们在聊天时一般不会特意使用一些标点符号，例如感叹号"!"来表示需要特别注意，冒号":"来表示要加的内容等。因为话语蕴含的意思通常可以通过上下文来“隐晦地”得到，这些规范的标点符号的用法通常在我们上高中或者大学时就被全部丢出大脑了。然而，在写提示词时，说话像一个“标准”的人会对 AI 理解文本含义，强化某些观念有更好的效果。例如我在修理纠缠在一起的三个 bug 时的提示词：

-   问题并没有解决！请同时考虑其他所有相关的文件和代码，充分考虑执行逻辑和 css 样式设置，继续修复问题。

这里也同时对 AI 进行引导，告诉它在其他地方也可能出错，而这会与现在的问题冲突导致不能完全修复，要充分考虑其他事项来完成问题修复。

> **提示词应当简洁而高效，带有尽可能少的不确定性和模糊性**

清晰地告诉 ai 现在已经完成的结果，使用转折词告诉它下面的任务或者问题。
